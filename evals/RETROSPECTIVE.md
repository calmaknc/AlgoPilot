# Agent Benchmark：重大案例复盘与简历口径

更新：2026-11-11（北京时间）。本文件只保留具有系统性意义的失败、修复和指标，不收录零散措辞、格式、算式或复杂度细节错误。历史完整报告仍保留，便于审计。

## 项目主线

基于个人Hot 100笔记和真实学习对话构建30条、63轮开发回归任务，重点考察工具使用、SQLite笔记操作、跨会话记忆、检索、多轮学习及调试，不把它包装成独立保留集或通用能力测试。

评分分为两层：脚本检查数据库/记忆状态、工具记录、检索集合及隐藏代码测试；AI基于真实回复与轨迹逐项复核语义，再汇总核心任务成功与解释质量。当前逐条语义评审实际由Codex完成，用户参与评分口径校准，不应声称已有独立人工双评或经过校准的独立LLM-as-a-judge系统。

简历主线为：构建真实工作流benchmark → 自动评分与证据复核 → 定位记忆与执行流程bug → 实现修复 → 定向回归验证。

## 案例一：记忆没有写入，却承诺“已记住”

**现象。** 首轮挑战25中，用户要求记住两项偏好，回复确认成功，但afterMemory只有空索引；记忆提取报告“记忆更新操作格式或数量不正确”。后续新会话没有召回目标偏好。第四轮要求定向修改时再次错误确认成功。

**根因。** 成功承诺与实际提交顺序脱节，主回答没有依赖最终写入结果。记忆提取格式错误是触发条件，真正的可靠性缺陷是“未提交即可确认”。

**修复。** 将用户偏好提取、校验与提交前置到主回答之前，再召回最新记忆。返回updated/unchanged/failed结构化结果并注入主模型；格式或来源校验不合格时最多修正一次，服务或存储故障不盲目重试。回答后的记忆提取只处理新成功工具事实，不再次应用用户偏好。

**验证。** 单独复测25，检查五个新会话共享的记忆快照和回复，确认保存、召回和定向更新。后续30条全量评测中18和25核心均通过。仍只是在已覆盖场景中验证，不承诺完全消除模型错误确认。

证据：[最初失败](REPORT-challenge-2026-11-11.md)、[修复及复测](REPORT-memory-25-2026-11-11.md)。

## 案例二：把临时指令写入长期偏好

**现象。** 用户要求记住两条长期偏好，同时说“本任务只回复确认，不建立刷题笔记”。第一次记忆修复后，临时要求也被存为跨会话project记忆条目no-problem-solving-notes。

**根因。** 对同一消息中的指令没有按作用域分别判断，将“记住其中两项”扩大成“整段内容都值得长期保存”。

**修复。** 提取提示按句区分稳定偏好、当前轮例外及事实；增加isTemporaryPreference校验，拦截明显仅本次/本轮/本任务有效的user/behavior偏好候选。利用一次有限修正移除临时候选、保留合法偏好。该规则不是完备语义分类器，也没有对已有project/reference记忆做全量清理。

**验证。** 后续25复测中五轮仅保留两项目标偏好，临时完整解法请求不覆盖旧偏好，永久修改仅更新指定一项；30条全量中18、25核心通过。

证据：[作用域修复](REPORT-memory-scope-hints-2026-11-11.md)。历史报告中的旧严格总评还包含提示篇幅等争议，现行核心结果应参照[重评口径](REASSESSMENT-POLICY.md)。

## 案例三：工具循环用完预算，任务中途终止

**现象。** 全量中的24、27、29、30、32、33有6个对话轮报错，24后续一轮未发送。部分任务已经写入笔记，却没有最终交付，错误统一为“模型调用失败，本轮未保存”。

**机制。** requestModel原先最多5次主模型请求，第5次若继续要求工具则直接抛错，没有强制收尾机会；service又掩盖底层错误。旧日志与预算耗尽一致，但原始异常丢失，不能严格证明6次都因同一原因。

**修复。** 提高到12次主请求，前11次允许工具，第12次tool_choice=none要求根据已有证据作最终回复、说明未完成事项；提供当前预算提示。保留具体消息、错误码及cause，区分对话未保存与已提交工具副作用。末轮仍要求工具时不执行并明确报错，空回复不能靠此前过程文本伪装完成。

**验证。** 同6条复测13/13轮全部完成，执行报错6→0，核心0/6→5/6，接雨水隐藏测试74/74通过。本轮最多6次主请求，未真实触发第12次收尾，末轮机制由模拟测试覆盖。预算提示与随机性也改变了路径，不能把所有改善单独归因于上限。

证据：[全量报告](REPORT-full-v1.5-2026-11-11.md)、[定向复测](REPORT-budget-six-2026-11-11.md)。

## 案例四：17误删笔记，操作历史叙述不实（尚未修复）

**现象。** 查询命中正式笔记h100-3与草稿h100-3-draft，首轮未经澄清删除正式笔记。次轮删除用户指定草稿后，否认此前正式笔记已删除，最后两条都消失。

**分类。** 这是执行了错误操作及错误描述历史，不是程序抛异常意义上的“运行报错”。只影响评测库，真实笔记未改动。

**启示。** 提示中已有歧义澄清要求，仍不足以保障破坏性工具行为；应考虑在操作边界校验明确目标，并使用真实操作日志解释状态。当前仅记录，按用户要求未修复、未重跑17。

证据：[17首轮](runs/2026-11-11T13-21-46.773Z/17-delete-ambiguous-note-turn-1.json)、[17次轮](runs/2026-11-11T13-21-46.773Z/17-delete-ambiguous-note-turn-2.json)。

## 案例五：27答案找全，证据核验不足（保留观察，不直接认定产品bug）

**现象。** 复测中10篇主列表全部找对，precision=recall=100%；15次搜索，但仅读取42和189两篇全文，8篇只有摘要。按现有requireFullRead规则未通过。

**解释。** 这是“正确答案”与“规定的证据核验过程”之间的差异。摘要足够时逐篇全文读取未必更符合用户体验，因此用户不认为它必然是产品问题；保留当前成绩，不事后改规则，也不把它称为漏检8篇题目。

**可研究方向。** 根据任务风险和摘要信息量决定是否补读，比较检索覆盖、来源证据充分性、工具次数、token与延迟。重要修改前应读全文；只找题目列表时可能允许摘要支持，但需要另立版本和评分标准。重复搜索不等于更深入核验。

**适用范围。** 27主要调用个人笔记search/get工具，并非联网搜索；可以启发联网检索中的“搜索结果摘要vs原网页”策略，但当前证据不能直接评价联网检索力度。32只看24/32篇摘要却声称全部，也是检索覆盖声明与实际证据不一致的相关观察。

证据：[27检索评分](runs/2026-11-11T13-54-42.826Z/retrieval-grades.json)、[27原始轨迹与回复](runs/2026-11-11T13-54-42.826Z/27-retrieve-two-pointers-turn-1.json)。

## 可报告的指标

| 指标 | 当前结果 | 解释限制 |
|---|---|---|
| 全量任务单次成功率（empirical pass@1） | 23/30，76.7% | 增加循环预算前的30条全量结果；每条一次尝试 |
| 修复后失败子集单次成功率 | 5/6，83.3% | 针对先前失败项，不代表全量能力；不能与旧24条拼接 |
| 子集对话轮完成率 | 13/13，100% | 执行完成不等于语义任务通过 |
| 代码隐藏样例通过率 | 全量493/493；复测74/74 | 样例通过率，不是任务pass@k |
| pass@3 / pass@5 | 尚未测量 | 不能用改了代码、提示或规则的历史重跑拼接 |
| 子集执行耗时/token | 303.641秒；584,840 token | 13轮合计，usage完整，包含记忆调用；非账单费用 |
| 全量执行耗时/token | 958.741秒；已观测1,363,325 token | usage不完整，仅能报告已观测下界 |

pass@k表示同一任务在固定配置下k次候选尝试至少一次成功的能力；一条多轮任务完整执行才算一次尝试，不是一轮模型请求算一次。推广到有状态Agent时，每次应重置相同的SQLite/记忆初态、隔离副作用，并固定模型、提示、预算和评分。应对全套任务采样，不能只对失败任务重复后挑最好结果。

若未来每题采样n次、成功c次，n≥k时可使用1-C(n-c,k)/C(n,k)再对任务平均的估计；c<n时不能凭空外推没有采样的k。当前每题只有一次同配置全量样本，优先写“单次任务成功率76.7%”，可附empirical pass@1，不把它描述为稳定成功概率。定义参考：[HumanEval论文](https://arxiv.org/abs/2107.03374)。对实际助手，还应同时报告所有重复均成功的任务比例，避免“多试几次总有一次成功”掩盖不稳定性。

## 简历建议用语

- 基于个人Hot 100笔记及真实学习对话，构建30条、63轮Agent工作流benchmark，覆盖笔记检索与操作、跨会话偏好、多轮调试与学习；结合脚本状态检查、493个隐藏样例与AI证据复核评估任务成功。
- 基于评测修复长期记忆提交与回复确认顺序脱节、临时指令污染长期偏好问题，通过提交前置、结构化结果传递及作用域校验，验证跨会话保留和定向更新。
- 优化Agent Loop预算与错误可观测性，预留最终回复并保留底层异常；对6条原执行失败任务定向复测，13/13轮正常完成、5/6任务通过。全量初测单次成功率76.7%，持续记录token及延迟。
