## 我的思路与追问

建立字典，key 表示组成单词的字母及其出现次数，value 是该组字符串列表。本人先询问该设计是否违反 Python 字典语法、是否能优化，之后自行实现以下版本，认为低效并希望优化。

字典组织方式正确。两个字符串是异位词，当且仅当各字符出现次数相同。仅记录出现过哪些字母而不记录次数是不够的，例如 `ab` 与 `aab` 不应归为一组。

## 我的总结：难点在于找到可哈希的规范化表示

本人总结：这题的难点是找到一种数据结构，使相同字母组成的单词具有相同的表示，最好还可哈希。

更准确地说，表示必须保留每个字母的出现次数，并满足：两个单词的 key 相同，当且仅当它们是字母异位词。前一方向保证同类能合并，后一方向保证不同类不会误合并。

例如 `eat` 与 `tea` 应得到同一 key；`ab` 与 `aab` 必须得到不同 key，所以仅用字母集合不够。

- 排序后的字符串：通过统一字符排列顺序获得相同表示。
- 排序后的 `(字符, 次数)` 元组：通过统一计数项顺序获得相同表示。
- 固定 26 位计数元组：通过固定字母位置获得相同表示。

前面的步骤解决“如何判断属于同一类”，可哈希的 key 则让字典能高效完成分组。这种将对象转换为统一表示的方法称为规范化，可用于其他按某种等价关系分组的问题。

## 我的原始代码

```python
class Solution:
    def groupAnagrams(self, strs: list[str]) -> list[list[str]]:
        record = {}
        for s in strs:
            unique = tuple(sorted(Counter(s).items()))
            if unique in record:
                record[unique].append(s)
            else:
                record[unique] = [s]

        return list(record.values())
```

本地独立运行时需导入 `from collections import Counter`。

`Counter(s).items()` 给出字符和计数，排序使 key 与字符首次出现的顺序无关；外层 tuple 和内部的 `(字符, 整数)` 元组都可哈希，可以作为字典键。本实现逻辑正确。

## 优化：用固定位置代替排序

本题只包含小写英文字母，因此建立长度为 26 的数组，每个位置分别代表 a～z 的出现次数。最后转成 tuple，作为字典键。

例如只展示 a、b、c 三个计数位置：

```text
ab  → (1, 1, 0, ...)
ba  → (1, 1, 0, ...)  同一组
aab → (2, 1, 0, ...)  不同组
```

固定位置已经明确表达每个计数属于哪个字母，不必再保存字符标签或排序。列表不可直接用作字典键，但由整数组成的 tuple 可以。

```python
from collections import defaultdict

class Solution:
    def groupAnagrams(self, strs: list[str]) -> list[list[str]]:
        record = defaultdict(list)
        for s in strs:
            counts = [0] * 26
            for ch in s:
                counts[ord(ch) - ord('a')] += 1
            record[tuple(counts)].append(s)

        return list(record.values())
```

以上为助手此前给出的参考实现。本人反馈已按该思路重写并提交通过，但未提供重写后的源码，因此不将此代码冒充为本人的完整提交代码。

`defaultdict(list)` 在键不存在时自动创建一个新列表，使分组操作只需一行；这是简化代码，不改变核心算法复杂度。空字符串对应全零元组，自然归到同一组。

## 原版并非非常低效

设 N 为字符串数量，T 为所有字符串总长度，d 为某个字符串的不同字符数。

- 原版对一个长度 L 的字符串，计数与构造／哈希 key 耗时约 O(L+d log(d+1))；排序的是不同字符的计数项，不是全部 L 个字符。
- 本题 d 不超过 26，因此原版总时间也是 O(T+N)，并不是必须优化才能达到线性复杂度。
- 计数数组版时间为 O(T+26N)，固定字母表下同样是 O(T+N)。它省去了排序和字符计数对的构造，但每个字符串会初始化并处理 26 个计数位置。
- 因此这是利用输入范围替换 key 表示的方法，不能仅根据复杂度断言 Python 实测一定更快，短字符串时尤其如此。本次未做性能对比。
- 计数数组版的分组存储约 O(N+26G)，G 是组数；其中 N 为字符串引用数量，26G 为 key 的计数数量。不复制字符串内容。固定字母表下可写 O(N)，当前计数数组只需 O(26) 空间。

## 通过后的追问：还有没有其他算法可以更快？

### 复杂度已经达到线性

对一般输入，正确分组在最坏情况下必须检查所有字符，还需要处理每个字符串（包括空字符串）。因此通常的逐字符访问模型下，下界为 Ω(T+N)，当前计数法的 O(T+N) 已经达到这个量级。继续改进主要是常数、key 的存储方式和 Python 的执行开销。

### 另一种标准算法：排序字符串作为 key

```python
from collections import defaultdict

class Solution:
    def groupAnagrams(self, strs: list[str]) -> list[list[str]]:
        record = defaultdict(list)
        for s in strs:
            key = ''.join(sorted(s))
            record[key].append(s)
        return list(record.values())
```

`eat`、`tea`、`ate` 排序后都是 `aet`。这是对整个字符串排序，区别于本人原版只排序 Counter 的不同字符项。

设第 i 个字符串长度为 L_i，总时间上界约 O(N+Σ L_i log(L_i+1))。它写法简洁，但并没有比计数法更好的渐进复杂度。实际运行快慢需要测量，不能仅凭复杂度或某次提交的排名断言；本次未做性能对比。

### 更紧凑的计数 key：bytes

保留计数过程，只把：

```python
record[tuple(counts)].append(s)
```

换为：

```python
record[bytes(counts)].append(s)
```

`bytes` 是可哈希的不可变字节序列，每个计数占一个字节。它精确保存 26 个计数，不是会丢失信息的摘要。本题每个字符串长度最多为 100，所以计数均在 0～100，满足 bytes 要求的 0～255 范围。

这能让 key 的表示更紧凑，但不是新算法，也不保证运行时间更短。若推广到单字母可能重复 256 次或更多的输入，不能直接使用这种表示。
